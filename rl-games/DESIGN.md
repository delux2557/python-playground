# 强化学习入门项目 · 设计文档

> 一句话目标:**用 DQN 训练一个会玩游戏的强化模型,把"模型到底在想什么"实时可视化,最后演进到人和模型同屏对战。**

- 技术路线:**贪吃蛇(入门热身)→ 黑白棋(人机对战)** ,全程**手写 DQN(PyTorch)** + **Web 可视化**
- 目标读者:学过机器学习入门、第一次做强化学习项目的新手
- 阅读顺序:第 1~3 章建立全局认知 → 第 4 章(贪吃蛇)是第一步 → 第 5 章(黑白棋)是第二步 → 第 6 章界面 → 第 7 章平台协议 → 第 8 章调参速查

---

## 1. 项目总览

### 1.1 我们要解决什么问题

| 你的需求 | 对应的设计决策 |
|---|---|
| 模型会玩游戏 | 手写 DQN(值函数方法),训练一个策略 |
| 能看到过程 | Web 实时渲染游戏画面 |
| 人也能玩 | 界面提供"人玩"模式,键盘/鼠标操作 |
| 能看到模型在干什么 | "模型驾驶舱":实时展示观察输入、Q 值排序、选中动作、ε 等内部状态 |
| 人和模型对战 | 第二步换回合制棋盘游戏(黑白棋),同棋盘轮流落子 |

### 1.2 两阶段路线图

```
Phase 1 · 贪吃蛇(DQN 入门)          Phase 2 · 黑白棋(人机对战)
─────────────────────────────      ─────────────────────────────
环境 env.py                        环境 env.py(合法落子掩码)
DQN(dqn.py)                        自对弈 self-play 训练
训练 train.py(看收敛曲线)            对战 serve + Web 界面
Web 驾驶舱(模型玩/人玩/遥测)           人机轮流落子 + 决策遥测
```

选这两个游戏的理由:
- **贪吃蛇**:动作空间小(4 方向)、一局几十秒、奖励直观,十几分钟就能看到模型"从瞎撞到会吃",是体验 RL 学习的"首胜"。
- **黑白棋(Reversi)**:8×8 小棋盘、合法动作天然受限、终局子数就是自然奖励,同一棋盘上人和模型轮流落子,是最自然的人机对战形式。比五子棋(15×15、动作空间大、奖励稀疏)更适合入门。

### 1.3 技术栈选型理由

| 层 | 选择 | 为什么 |
|---|---|---|
| 语言 | Python 3.10+ | 生态最全,学习资料最多 |
| 深度学习 | PyTorch 2.x | 业界事实标准,张量操作直观,便于手写 DQN |
| 环境接口 | Gymnasium 风格 | OpenAI Gym 官方继任者;把"游戏逻辑"和"算法"解耦,环境可复用到别的游戏 |
| 算法 | 手写 DQN | 入门必修:经验回放、目标网络、ε-greedy 三个技巧贯穿所有现代 RL |
| 后端 | FastAPI | 轻量、类型友好,提供游戏状态/模型推理/遥测 API |
| 前端 | HTML5 Canvas + 原生 JS | 无构建负担,实时渲染游戏画面和驾驶舱面板 |
| 训练观测 | matplotlib / JSON 曲线 | 直观看到每局得分收敛 |

## 3. 核心概念速通(写给新手)

强化学习四要素:

| 概念 | 符号 | 通俗解释 | 在贪吃蛇里的例子 |
|---|---|---|---|
| 状态 | s | 模型"看到"的一帧信息 | 蛇头四周是否撞墙、食物在哪个方向 |
| 动作 | a | 模型可选的操作 | 上 / 下 / 左 / 右 |
| 奖励 | r | 每个动作后的即时反馈 | 吃到食物 +10,撞墙死亡 -10 |
| 策略 | π | "看到 s 就选 a"的规则 | Q 网络本身 |

**DQN 的三个关键技巧**(背下来,它们是所有深度 RL 的地基):

1. **经验回放(Experience Replay)** —— 把每一步 `(s, a, r, s')` 存进一个大缓冲池,训练时随机抽样。作用:打破相邻样本的强相关性,让网络学得更稳。→ 由 `buffer_size` 控制。
2. **目标网络(Target Network)** —— 用一份"延迟更新"的网络参数来算目标 Q 值。作用:避免"自己追自己"导致的 Q 值发散。→ 由 `target_update_freq` 或 `tau` 控制。
3. **ε-greedy 探索** —— 以概率 ε 随机乱走、否则按 Q 值选最优。作用:保证模型见过足够多样的局面。→ 由 `epsilon_start / epsilon_end / epsilon_decay` 控制。

**为什么游戏要能"秒级重置":** RL 靠海量试错学习,一个贪吃蛇环境每秒能跑几百上千局。环境的 `reset()` 必须极快,这是"入门选小游戏"的根本原因。

## 4. Phase 1 · 贪吃蛇

### 4.1 环境设计(`env.py`)

**状态表示(observation)—— 两种方案,推荐方案 A:**

- **方案 A:特征向量(推荐)**。输入一个 11 维向量:
  1. 蛇头正上方/正下方/正左/正右是否撞墙或撞自己(4 个 0/1,告诉模型"往哪走会死")
  2. 食物相对蛇头的方向:`dx / dy` 的归一化值(2 个连续值)
  3. 蛇头当前移动方向(4 个 0/1 one-hot)
  - 优点:网络小、训练快、状态少;缺点:信息是"人工提炼"的。
- **方案 B:网格图像**。把整个棋盘编码成一张小图(蛇身=1、食物=2),配 CNN。
  - 优点:更接近"模型看到的原始画面",驾驶舱里展示直观;缺点:慢、需要 CNN。
  - 本项目**先用方案 A 保证训练速度**,驾驶舱里再额外画一张"状态网格"辅助展示(见第 6 章)。

**动作空间:** 离散 4 个动作(上/下/左/右),并禁止直接 180° 掉头(否则模型会原地打转、白白送命)。

**奖励塑形(reward shaping)—— 参数决定性能的核心区:**

| 事件 | 奖励 | 为什么这么设 |
|---|---|---|
| 吃到食物 | `+10` | 主要学习信号,引导模型主动去吃 |
| 撞墙或撞自己 | `-10` | 强惩罚,让模型学会避开死亡 |
| 每走一步 | `-0.1` | 微小时间惩罚,防止模型在原地绕圈刷步数 |
| (可选)接近食物 | 无 | 保持奖励稀疏但清晰,入门阶段不加,避免学到奇怪策略 |

> 最佳实践提示:**奖励尺度要小**(数值在 -10 ~ +10 之间),否则 Q 值会爆炸,训练不稳定。这一行注释会写进 `env.py`。

### 4.2 DQN 算法(`dqn.py`)

**Q 网络结构(MLP):**

```
输入(11 维状态) → 全连接 64 → ReLU → 全连接 64 → ReLU → 输出(4 个 Q 值)
```

- 输出是 4 个数,分别代表"在这个状态下,往 4 个方向走的预期长期回报"。
- 训练时模型**选 Q 值最大的动作**(ε 之外),这就是"策略"。

**训练器内部(对应三个技巧):**

| 组件 | 实现要点 | 相关超参数 |
|---|---|---|
| 经验回放 | `deque(maxlen=buffer_size)`,训练时随机抽 `batch_size` 条 | `buffer_size`, `batch_size` |
| 目标网络 | 每 `target_update_freq` 步把在线网络参数拷贝给它 | `target_update_freq` |
| ε-greedy | ε 随训练步数从 `epsilon_start` 线性/指数衰减到 `epsilon_end` | `epsilon_start/end/decay` |
| 损失函数 | 用目标网络算 `target = r + γ·max(Q'(s'))`,和在线网络的 `Q(s,a)` 做 MSE | `gamma`(γ), `lr` |

### 4.3 训练流程(`train.py`)

```
循环:
  1. reset 环境,拿到初始状态 s
  2. ε-greedy 选动作 a → 环境返回 (s', r, done)
  3. 把 (s, a, r, s') 存入回放缓冲
  4. 从缓冲随机抽 batch,算 loss,反向传播更新网络
  5. 每隔 N 步把在线网络拷贝到目标网络
  6. 每隔 M 局跑一次"无探索评估"(ε=0),记录每局得分 → 画出收敛曲线
  7. 定期保存 checkpoint,便于随时用界面加载
```

**评估与训练分离**(最佳实践):训练用 ε-greedy 探索,评估用纯贪婪(ε=0),否则曲线会高估真实水平。

### 4.4 超参数与性能速查表(新手必读)

| 参数 | 含义 | 调大效果 | 调小效果 | 常见问题 |
|---|---|---|---|---|
| `lr` 学习率 | 每步更新幅度 | 学得快但易震荡/发散 | 稳但慢 | 不收敛先调小 lr |
| `gamma` γ | 对未来奖励的重视程度 | 更有远见但稀疏环境难学 | 短视,只看眼前 | 贪吃蛇取 0.95 附近 |
| `epsilon_start` | 初始探索率 | 探索多,前期瞎撞多 | 一开始就贪心,可能学不到全貌 | 一般从 1.0 开始 |
| `epsilon_decay` | 探索衰减速度 | 衰减慢,探索久 | 很快转入利用 | 衰减太快会错过好策略 |
| `buffer_size` | 经验池容量 | 样本多样、去相关,但占用内存 | 样本过旧/相关性高 | 一般 10_000~100_000 |
| `batch_size` | 每次训练的样本数 | 梯度更稳,但更吃显存 | 梯度噪声大 | 常用 32~128 |
| `target_update_freq` | 目标网络更新间隔 | 目标更稳定但更新慢 | 目标跟得紧但易震荡 | 常用 100~1000 步 |
| 网络宽度(64/128) | 单层神经元数 | 表达能力更强 | 欠拟合(学不会) | 贪吃蛇 64~128 足够,再大只会更慢 |

## 5. Phase 2 · 黑白棋(人机对战)

### 5.1 为什么换玩法

贪吃蛇是**单人决策**;黑白棋是**双人零和博弈**——你的赢就是对手的输。单人项目里"练得强"就够了,双人项目里对手也在变强,所以训练方式升级为**自对弈(self-play)**:让模型跟自己(或比自己弱一点的历史版本)下棋,互相磨炼。

### 5.2 环境设计(`env.py`)

| 设计点 | 方案 | 说明 |
|---|---|---|
| 状态表示 | 8×8 棋盘编码成 3 通道图(己方/对方/空),或展平成向量 | 与贪吃蛇不同,黑白棋需要"全局局面"信息 |
| 动作空间 | 64 个格点 + **合法动作掩码(legal mask)** | 非法落子处强制 Q 值为 `-∞`,模型只能选合法位置 |
| 奖励 | 终局才给:`+1` 赢、`-1` 输、`0` 平;每步 0 | 稀疏但干净,避免引导出"只看眼前子数"的短视策略 |
| 胜负判据 | 终局子数多者胜 | 这就是人机对战的计分规则 |

### 5.3 自对弈训练(`selfplay.py`)

```
循环:
  1. 当前模型 vs 对手池中的某个模型(如上一个 checkpoint)
  2. 双方各自 ε-greedy 落子,直到终局
  3. 用终局结果给整局每一步打标签:赢 +1 / 输 -1
  4. 存入回放,训练更新
  5. 定期把当前模型存进对手池,淘汰最旧的版本
```

**为什么要"打对手池"而不是一直打自己最新版:** 一直打最新版会导致策略"原地打转"(两个模型互相 exploit 同一个漏洞)。打历史版本(经典做法,类似 AlphaGo 的采样机制)能让策略稳定提升。这是黑白棋阶段最重要的最佳实践之一。

### 5.4 与贪吃蛇 DQN 的差异

| 维度 | 贪吃蛇 | 黑白棋 |
|---|---|---|
| 博弈类型 | 单人决策 | 双人零和 |
| 训练方式 | 自己 vs 环境 | 自己 vs 对手池(自对弈) |
| 奖励时机 | 每步都有信号 | 只在终局给信号 |
| 动作约束 | 4 个方向 | 64 格 + 合法掩码 |
| 评估指标 | 每局得分 | 对战胜率(打固定对手或人) |
| 驾驶舱重点 | Q 值排序 | 当前局面评估 + 候选落子 Q 值分布 |

## 6. Web 界面设计(驾驶舱)

### 6.1 驾驶舱面板对应模型的内部状态

| 驾驶舱面板 | 前端展示 | 来自后端哪份数据 |
|---|---|---|
| 游戏画面 | Canvas 实时渲染棋盘/蛇 | `GET /api/state`(游戏状态) |
| 本次决策 | 4 条 Q 值条 + 高亮选中动作 + 上一步奖励 + 当前 ε | `POST /api/step` 返回值里的 `q_values / action / reward / epsilon` |
| 模型观察输入 | 状态网格图(蛇身/蛇头/食物) | `observation`(模型实际输入) |
| 训练参数 | ε、γ、lr、网络结构 | `GET /api/config` |
| 训练曲线 | 每局得分折线 + 平均/最高分 | `GET /api/curve`(训练时攒下的历史) |

### 6.2 三种模式

| 模式 | 谁下决策 | 实现方式 |
|---|---|---|
| 模型玩 | 模型 | 前端定时调 `POST /api/step`,后端跑一次推理 |
| 人玩 | 人 | 前端捕获键盘/鼠标,把人类动作作为 `action` 传给后端,后端照样返回新状态和奖励(让"人的每一步"也走同一套接口,方便对比) |
| 人机对战(黑白棋) | 轮流 | 前端按当前轮到谁,决定是"人输入"还是"调模型推理" |

### 6.3 前端技术要点

- 游戏画面用 **Canvas + requestAnimationFrame**,帧率上限 30fps,避免训练卡顿。
- 提供**速度控制**(×1/×4/暂停/单步),训练时用高速,讲解时慢放。
- 驾驶舱数据用 **WebSocket 或短轮询** 推送,不阻塞画面。
- 视觉风格:统一的 token 化设计系统(品牌紫 + 中性面),保证"模型玩/人玩/对战"三套界面观感一致。

## 7. 平台协议:让 Web 与训练解耦、模型可切换

> 这是本项目的"平台化"核心。目标是:**同一套 Web 界面能服务任何游戏、任何算法、任何已训练模型**——换游戏/换算法/换模型时,前端一行都不用改。

### 7.1 我们要解决什么问题

单机版贪吃蛇服务把"游戏逻辑、模型推理、HTTP 路由、前端渲染"全都写在一个 `serve.py` 里,一旦换成黑白棋就要重写一遍。平台化就是把这些拆开:

- **前端不再写死任何游戏细节**,一切由后端"自报家门"(元数据)决定;
- **后端服务抽象成统一协议**,每个游戏只实现 6 个"游戏特有"方法;
- **训练产出的模型登记进注册表**,前端下拉框随时切换,后台训练与前台推理解耦。

**业内的成熟做法**:OpenAI Gymnasium(统一环境接口)、Stable-Baselines3(统一算法接口)、Unity ML-Agents(统一 Agent 协议)。本项目用最小化的方式复刻这一思想,目的是让新手看懂"协议"到底是怎么让系统可插拔的。

### 7.2 三层契约(`shared/protocol.py`)

| 层 | 定义 | 作用 |
|---|---|---|
| `StepRequest` | 前端"走一步"请求的统一格式:`{"ai": true}` 或 `{"action": 0~3}` | 模型玩 / 人玩共用同一个接口 |
| `AgentService` | 抽象基类,每个游戏实现 6 个方法(见 7.3) | 把"游戏特有"的东西全部收拢到子类 |
| `build_app()` | 把任意 `AgentService` 包装成一套标准 FastAPI 路由 | 所有游戏共用同一套 URL 和返回结构 |

### 7.3 每个游戏只需实现 6 个方法

| 方法 | 返回什么 | 新手怎么理解 |
|---|---|---|
| `meta()` | 元数据:棋盘怎么画、动作有几个、观察每维什么意思 | 前端"如何渲染"的说明书 |
| `snapshot()` | 当前局面 + 观察 + Q 值 + ε + 模型信息 | 驾驶舱面板的全部数据 |
| `reset()` | 开局,结构与 snapshot 相同 | 点击"重新开始" |
| `step()` | 走一步的完整记录(观察 / Q值 / 动作 / 奖励 / 是否结束) | 模型玩或人玩的每一步 |
| `curve()` | 训练曲线 `{"episodes": [...], "scores": [...]}` | 画训练折线图 |
| `_load_weights()` | 把 checkpoint 加载进自己的网络 | 换模型的唯一入口 |

**为什么抽象成这 6 个?** 因为任何"可玩的强化学习游戏"都逃不出这 6 件事:描述自己、看局面、开局、走一步、回顾历史、换模型。抽出来之后,换游戏只是"再实现一遍这 6 个方法",协议层和前端一行都不用改。

### 7.4 标准路由(所有游戏一致)

```
GET  /api/meta            元数据(棋盘/动作/观察含义) + 已登记模型
GET  /api/state           当前局面 + 模型看到的一切(观察 + Q 值 + ε)
POST /api/reset           开局
POST /api/step            走一步 {"ai":true} 或 {"action":0~3}
GET  /api/curve           训练曲线
GET  /api/config          训练超参数
GET  /api/model           当前加载的模型信息
GET  /api/models          模型注册表列表
POST /api/models/load     切换模型 {"name": "模型key或路径"}
GET  /api/train/status    训练进程实时状态(见 7.5 训练/Web 解耦)
```

前端启动时先调 `GET /api/meta`,拿到元数据 + 模型列表,剩下的一切(画棋盘、渲染 Q 值条、填充模型下拉框)都由元数据驱动——这就是"换游戏前端零改动"的秘密。

### 7.5 训练/Web 解耦(训练进程只写、Web 只读)

**要解决的问题:** 训练(练几小时)和 Web(看对战)如果挤在同一个进程里,会互相阻塞:训练时页面卡死,或 Web 开着时没法启动训练。更糟的是用"共享内存 + 线程"做耦合,崩溃一个就全崩。

**我们的方案:** 训练和 Web 是两个**独立进程**,不共享内存,只通过两份文件通信——

```
训练进程(train.py)                        Web 进程(serve.py)
────────────────────────                 ─────────────────────
ProgressReporter                          /api/train/status
  ├─ 原子写 data/othello_progress.json ──► 读进度(状态/局数/胜率/ε/对手池)
  └─ 原子写 data/othello_curve.json   ───► /api/curve 读曲线
```

- `progress.json` 记录状态机:`starting → running → done/error`,每次评估更新一次;
- `curve.json` 记录胜率曲线,每次评估**追加一个点**(增量写),Web 端曲线跟着动;
- **原子写**(先写 `.tmp` 再 `os.replace`):Web 随时读,永远读到完整 JSON,不会读到"写了一半";
- `AgentService.train_status()` 是协议层的**可选第 7 个钩子**(默认返回 idle),游戏覆盖它去读自己的进度文件——黑白棋覆盖了,贪吃蛇用默认实现;
- 前端每 **2 秒**轮询 `/api/train/status`,跑着就顺带刷新曲线,实现"训练进度实时可见"。

这样训练进程怎么跑、什么时候挂掉,Web 进程完全不受影响;反过来 Web 重启也不会打断训练。**进程隔离 + 文件契约**,这是最朴素也最稳的解耦方式,后面换成 Redis/消息队列也只是换"通信层"。

### 7.6 模型注册表(`shared/registry.py`)

**为什么需要它:** 模型文件散落在磁盘上,前端不知道"有哪些模型、谁更厉害"。注册表就是模型的"账本":训练脚本存模型时自动登记一条记录,前端通过注册表列出并切换。

| 字段 | 含义 |
|---|---|
| `key` | 唯一标识,`{game}-{时间戳到微秒}`,如 `snake-20260827-143012-345678` |
| `game` | 模型所属游戏 |
| `algorithm` | 用的什么算法(如 dqn) |
| `path` | checkpoint 文件路径(相对项目根) |
| `hidden_dims` | 网络结构 |
| `eval_score` | 评估分(如贪吃蛇平均分),方便对比不同模型 |
| `episodes` | 训练了多少局 |
| `created_at` | 登记时间,用于按新到旧排序 |

两个关键设计点(新手注意):

1. **key 必须唯一**:时间戳精确到微秒,否则同一秒内训练两个模型会互相覆盖;
2. **切换前校验文件存在**:注册表里登记的路径若已被删除,`resolve()` 返回 `None`,前端走 404,而不是 torch.load 报一堆底层错误。

### 7.7 会话隔离:每个标签页一局独立的棋

**要解决的问题:** 服务端如果只维护"一份全局游戏状态",多个浏览器标签页会共用同一条蛇/同一盘棋,
按键互相覆盖(贪吃蛇会"漂移")、黑白棋互相踩棋。

**实现方式:** 前端用 `crypto.randomUUID()` 生成会话 ID(存 `sessionStorage`),
每次请求带 `X-Session-Id` 头;协议层把它透传给服务方法(`snapshot/reset/step/load_model`
都有 `session` 参数);每个服务维护一张**会话表** `session_id → 游戏环境`,各自独立一局。

**分界原则(重要):**
- **按会话隔离**:对局局面(蛇的状态、棋盘、悔棋历史、人执哪色)。
- **全局共享**:模型权重、训练曲线、注册表、对战(duel)、竞技场(arena)、评测(benchmark)。

**生命周期:** 会话 30 分钟无活动自动回收(TTL);上限 256 个(`_MAX_SESSIONS`),超限返回 429;
不带会话头的请求(如 curl 测试)落到 `default` 会话。

**注意:** `GET /api/state` 会惰性创建会话(前端首屏必须拿到状态),这是设计取舍而非 bug。

### 7.8 如何新增一个游戏(三步走)

```
第一步:写游戏环境 env.py(Gymnasium 风格 reset/step/observation)
第二步:写训练脚本 train.py,存模型时调用 registry.register() 登记
第三步:写一个 AgentService 子类 serve.py,实现那 6 个方法,
        然后 app = build_app(MyService(), static_dir) 就完成了
```

> 这就是"可复用的学习、训练平台":换游戏只是换 `env + train + 6 个方法`,协议层、注册表、前端三件套全部复用。

### 7.9 对局平台抽象:Player / GameAdapter / Match(`shared/platform.py`)

协议层(7.2~7.8)解决的是"Web 服务标准化";平台层再进一步,解决
**"谁都能接入对局"**——训练模型、人类玩家、随机基线、未来的训练器,
都以同一种方式参与同一套对局引擎。这是业内"环境/智能体分离"的标准形态
(对应 Gymnasium 的 Env、ML-Agents 的 Behavior、PettingZoo 的 AEC 仲裁)。

三个核心抽象:

```
Player(参与方)      人 / 模型 / 训练器 / 随机基线,统一接口:
                    decide(obs, legal_mask) -> action
                    ├─ ModelPlayer : 包一个 DQNAgent,decide = select_action
                    ├─ RandomPlayer: 合法动作里随机挑(评测地板)
                    └─ HumanPlayer : 动作由外部 submit() 注入(异步房间/测试)

GameAdapter(游戏插件) 纯规则、无状态:
                    new_game / current_player / observe / legal_mask /
                    apply / done / result
                    └─ OthelloAdapter(othello/adapter.py)是第一个实现

Match(一场对局)    把 N 个 Player 放到一个 GameAdapter 上:
                    · play()          同步打完整局(对战/竞技场/自对弈)
                    · act()/auto_step() 逐步驱动(Web 人机对战)
                    · 人类座位不放 Player → auto_step() 抛 KeyError,
                      这就是"回合秩序"的天然防线
```

分工原则(重要):
- **新增游戏** = 写一个 `GameAdapter`,平台自动获得对战/评测/打榜能力;
- **新增参与方** = 写一个 `Player`(模型、人、训练器都一样);
- **平台只做仲裁与编排**,不懂任何具体游戏规则。

训练热路径约定:训练时的高频自对弈在**进程内**直接调用
(`play_one` / `Match.play()`),不要把每步决策走网络——
平台负责"编排"(开对局、派任务、托管),不当训练的热路径。

现状:`othello/duel.py` 的 `_play_one` 与竞技场 `match_fn` 已改走
`Match + ModelPlayer`;`DuelSession.start()` 同时接受裸 `DQNAgent`
(自动包成 ModelPlayer)和 `Player`。人机对战的 HTTP 会话仍由
`OthelloService` 直接驱动 env(逐步交互带 Q 值展示),尚未迁到 Match——
那是下一步"通用对局观看器"的工作。

## 8. 调参速查(症状 → 解法,新手问答式)

| 现象 | 原因(最可能) | 怎么调 |
|---|---|---|
| 模型总是原地打转/绕圈 | 时间惩罚太重或没禁止 180° 掉头 | 检查 `-0.1/步` 是否过大、是否已禁止掉头 |
| 一直学不会(曲线不动) | 学习率太小 / 奖励尺度太小 | 调大 `lr` 或把奖励数值放大 |
| 训练发散/振荡(Q 值爆表) | 学习率太大 / 奖励过大 / 目标网络更新太快 | 调小 `lr`、缩小奖励值、增大 `target_update_freq` |
| 只会乱撞不利用所学 | ε 衰减太慢或 `epsilon_end` 太高 | 加快 `epsilon_decay`,把 `epsilon_end` 调到 0.01 附近 |
| 学到局部最优(只会一个方向) | 探索不足 | 提高 `epsilon_start` 或放慢衰减 |
| 黑白棋学到"只顾眼前子数" | 每步给了子数奖励 | 改回**只有终局奖励** |
| 黑白棋自己跟自己原地打转 | 一直打最新版本 | 改打对手池(历史 checkpoint) |
| 训练太慢 | 单局太长 / 网络太大 | 用加速模式、调小网络、把棋盘改小(如 6×6 实验) |

## 9. 常见坑与最佳实践清单

- [ ] 环境 `reset()` 和 `step()` 要足够快(性能是 RL 的第一生产力)
- [ ] 禁止 180° 掉头,避免无意义死循环
- [ ] 奖励尺度保持在小范围(±10),避免 Q 值爆炸
- [ ] 评估与训练分离:评估时必须 ε=0
- [ ] 每次运行固定随机种子(seed),保证结果可复现
- [ ] 定期保存 checkpoint,界面可加载任意版本对战
- [ ] 训练/推理服务分离时,模型要用 `eval()` 模式、关闭梯度
- [ ] 黑白棋合法动作掩码是必选项,否则模型会疯狂下非法棋
- [ ] 代码注释风格:面向新手,解释"这个模块/参数在干什么、调它会改变什么",不写废话注释

## 11. Docker 部署

**为什么适合上 Docker**:项目是"训练 + Web 服务"的标准形态,天然适合容器化——
训练是长任务、Web 是要常驻的对外服务,两者各自封装成一个容器后,
本机 `docker compose up -d` 一键起全套,换机器/上线也都是同一套命令。

**设计要点(和"训练/Web 解耦"一脉相承)**:
- 一个镜像两用:`web` 容器跑 uvicorn(只读),`worker` 容器跑训练(只写)。
- 通过两个**命名卷**(`models/`、`data/`)共享:worker 把模型、注册表、
  训练曲线、MLflow 库写进卷,web 容器直接读到——容器间不共享内存、
  不互相依赖,与文件解耦的设计完全一致。
- 训练完的模型登记进注册表后,web 界面即可切换加载、发起对战/评测。

**命令速查**:
```bash
docker compose up -d        # 构建并启动(黑白棋 :8001 / 贪吃蛇 :8002)
docker compose logs -f worker   # 看训练进度
docker compose down         # 停止(数据保留在命名卷)
docker volume ls            # 查看持久化的模型/数据卷
```

## 12. 演进路线(结合业内最佳实践)

项目已具备"环境 → 训练 → 平台化服务 → 可视化 → 评测打榜 → 部署"的完整骨架,
接下来的演进按"先把已有的做扎实,再扩展规模"的原则展开:

**P1 工程化(已完成)**
- MLflow 实验跟踪:每次训练记录超参数、指标、模型 artifact,实验可复现、可对比。

**P2 让"谁更强"有统一答案(已完成)**
- 统一评测基准(`shared/eval.py`):固定种子 + 固定局数,所有模型同一把尺子重打分。
- 循环赛打榜(`shared/arena.py`):全体模型两两对战、黑白各打一遍,按积分排总榜。
- 前端竞技场面板:一键重新评测 + 循环赛进度与排行榜实时刷新。

**P3 部署(已完成)**
- Docker Compose:web + 训练 worker 两条容器,本地一键起全套。

**P4 对局平台抽象(已完成)**
- `shared/platform.py`:Player / GameAdapter / Match 三层抽象,
  训练模型、人类、随机基线以"参与方"身份统一接入同一套对局引擎。
- `othello/adapter.py`:第一个 GameAdapter 实现;`duel` 与竞技场 `match_fn`
  已改走 `Match + ModelPlayer`(见 7.9 节)。

**P5 断点续训 + 前端工程化(已完成)**
- 断点续训(`shared/checkpoint.py`):训练过程中定期把"模型 + 已训练局数 +
  探索率"原子存档;下次启动自动检测 checkpoint,接着上次局数往下训,
  探索率从上次位置继续衰减,曲线连续。崩溃最多丢 eval_freq 局。
- 前端工程化:共享层 `shared/static/frontend/`(common.js/common.css)+
  两游戏前端拆成 ES Modules 多文件(见 README §3.9)。
- 部署修正:`.dockerignore` 让预训练模型进镜像,命名卷首次挂载自动带出。

**后续可选的演进方向(按性价比排序)**:
1. **通用对局观看器**:把人机对战的 HTTP 会话也迁到 `Match`(`act()`/`auto_step()`),
   前端改由 GameAdapter 的 meta 驱动渲染——新游戏注册即得完整对战界面。
2. **训练器作为参与方接入**:自对弈训练器实现 `Player.decide()` + `on_match_end()`,
   由平台编排对局(热路径仍在进程内),删掉 `selfplay.py` 里的手动回合循环。
3. **经验池/对手池快照续训**:目前的续训只恢复"权重 + 局数 + 探索率",
   经验池与对手池(othello)会从零重建;要做到"完全无感断点续训",
   需把 ReplayBuffer 与对手池也序列化进 checkpoint。
4. **CI 回归门槛**:每个 PR 自动跑一遍统一评测,新模型对旧模型胜率不劣于阈值才放行,
   防止"训练越改越弱"悄悄发生——这是业内"模型质量门禁"的最小实现。
5. **更强的算法**:从 DQN 自对弈升级到 AlphaZero 式 MCTS + 策略价值网络,
   黑白棋是验证它的天然实验场(先手优势、终局稀疏奖励、对称性增强)。
6. **分布式训练**:用 Ray 把自对弈收集与参数更新拆开,支持多 worker 并行采样
   ——小规模项目暂不需要,等训练时长成为瓶颈再引入。

## 附:代码注释风格约定

为了让新手看得懂,代码注释遵循以下规则(示例):
